## 問題解決の原則

- **暗黙的な fallback を書かない**: 問題が起きたときに「とりあえず動く」回避策を追加するのではなく、根本原因を特定して解決する
- **ワークアラウンドより根本解決**: エラーを握りつぶしたり、条件分岐で回避したりせず、なぜその問題が起きているのかを調査する
- **修正前に仮説を立てる**: 修正を提案する前に「何が原因だと考えるか」「どのファイル/関数が関係するか」を説明し、承認を得てから実装する

## AI としての行動規範

- **推測するな、コードで検証せよ**: 名前・値・動作は必ず実際のコードで確認する。記憶や推測で修正しない
- **「念のため」コードを書くな**: 未使用メソッド、将来用フィールド、単一実装のための抽象化は不要。YAGNI を徹底する
- **設計判断を勝手にしない**: 実装範囲を超える判断（新パターン導入、ファイル構成変更等）は確認を取る
- **同じ修正が3回繰り返されたらアプローチを変える**: 部分修正の繰り返しではなく代替案を提示する

## コード品質原則

- **起こり得ないシナリオに対するエラーハンドリング、フォールバック、バリデーションを追加しない**: 内部コードやフレームワークの保証を信頼する。バリデーションはシステム境界（ユーザー入力、外部API）でのみ行う
- **コメントは Why のみ**: What/How はコードで表現する。説明的コメントは書かない
- **Boy Scout Rule**: 触ったファイル内の小さな問題（数秒で直せるもの）は今修正する。「次のタスクで」に先送りしない
- **スコープクリープを避ける**: 要求されていない機能追加、不要な設定可能化、過剰な抽象化をしない
- **エラーハンドリングは集中化**: try-catch を散らばらせず、上位層で一括処理する

## フォールバック禁止の具体例

| 禁止パターン | 例 | 問題 |
|---|---|---|
| 必須データのフォールバック | `user?.id ?? 'unknown'` | エラー状態で処理が続行される |
| デフォルト引数の悪用 | 全呼び出し元が省略する `function f(x = 'default')` | 値の出処が不明 |
| try-catch で空を返す | `catch { return ''; }` | エラーの握りつぶし |

許容: 外部入力バリデーション時のデフォルト値、設定ファイルのオプショナル値

## デバッグガイドライン

データ表示の問題をデバッグする際は、修正を提案する前にまずデータが API から来るのか DB から来るのかを確認してください。データフローアーキテクチャについて明確化の質問をしてください。
