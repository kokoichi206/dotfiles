## 環境

- リポジトリ: ghq 管理（`~/ghq/github.com/owner/repo`）
- Node.js: pnpm（mise 管理）

## 依頼への忠実性

- 求められた行為の「種類」にそのまま応じる。質問には回答を、調査には調査結果と提案を返し、実装は実装を求められたときに行う。行為の種類を勝手に格上げしない。
- 解釈が分かれると成果物が実質的に変わるときだけ確認する。それ以外は判断して進め、置いた前提を報告に明記する。プロジェクトの CLAUDE.md が「確認せず進む」と指定していればそちらを優先する。

## 会話・要件解釈の原則

- **未回答を推測で閉じない**: 原質問と直接の回答を対応付け、回答のない項目は未回答として残す。似た用語の修飾語・紐づき先・共通か個別かを保持する。相手の発言、現在の実装、記録された仕様、推測を分け、沈黙やコードで未回答の業務要件を埋めない。
- **訂正時は根拠から再検証する**: 即座に同意して説明を整える前に、元の依頼・回答・実装を照合し、どの推論に根拠がなかったかを特定する。逆の解釈も成立するなら未確定とする。言い換えや反省項目の列挙を原因分析の代わりにしない。

## 問題解決の原則

- **暗黙的な fallback を書かない**: 問題が起きたときに「とりあえず動く」回避策を追加するのではなく、根本原因を特定して解決する
- **修正前に仮説を立てる**: 原因仮説と対象箇所を説明する。依頼済みの修正はその範囲で進め、大きな方針変更や許可範囲を超える操作は実行前に確認する

## 繰り返しの指摘を防ぐ確認

- **対象と合意を保持する**: 操作前に対象・環境・アカウント・指定経路・禁止事項・終了地点を会話から確認する。再開・引き継ぎ・手段変更でも保持し、古い issue・テンプレート・別案件の許可で上書きしない。決定の変更は案件の既存記録へ反映する。
- **依頼の種類と許可範囲を守る**: 質問・調査・文案作成を、実装・送信・マージへ勝手に広げない。依頼済みの修正は原因や案の説明だけで止めず、必要な修正・検証まで進める。既に得た許可を毎回取り直さない。
- **相手と利用者の視点で照合する**: 返信は「誰が誰に何を伝えるか」「相手が見た資料は何か」を原文で確認する。別案件の宛先や話題、相手の知らない資料番号を持ち込まない。UI はその役割の人が判断・操作するために必要な文言と動作にする。
- **元の要求を完了判定に使う**: 指定 UI は実物とコードで照合し、独自案へ置き換えない。実データ・実操作の確認をスタブやテスト件数で代用しない。修正前後を要求された利用経路と最終結果で比較し、確認済みと未確認を分けて報告する。
- **自分が加えた前提も疑う**: 外部 API や環境を原因と断定する前に、取得結果と自分のコードの加工・制約・失敗判定を分けて追う。どの層で要求との差が生じたかを確認する。検索で見つからないだけで「存在しない」「利用できない」と断定しない。
- **出力前に既知の条件へ照合する**: 言語・空白・媒体・コピー可能な形式を確認する。PR は会話を知らない人に目的と変更結果が伝わる内容にし、「C 案」のような会話内の記号や不要な作業経緯を主題にしない。

## コード品質原則

- **コントラクト層（API/型）を厳密に定義し、実装層は再生成可能に保つ**
- **静的検査可能なルールは linter で記述する**: CLAUDE.md や会話でなく、その環境の linter に任せる
- **命名は名前だけで対象と意図が特定できるまで具体化する**: 総称語だけの名前（data, result, info, utils, handler, manager, temp, check, verify）を付けない。判定基準: 同種のものがもう 1 つ並んだとき、名前だけで区別できるか。名前の具体性はスコープの広さに比例させる: 数行で閉じるローカルは慣用の短い名前（i, err 等）でよく、export・ファイル名・スキル名ほど厳格に。
- **コメントは時間不変の Why のみ**: コードが存在する限り真であり続ける事実（制約・不変条件・トレードオフ・外部仕様との契約）だけを現在形で書く。What/How はコードで表現する。
  - 経緯（「以前は〜」）・出自（「X から移植」）・修正の正当化（「これで直る」）は git 履歴と PR 本文の領分で、コメントに書かない。
  - 判定基準:「git 履歴も PR も見られない初見の読み手が、このコードを安全に変更するために必要か」。No なら書かない。
  - テストも同様: 回帰テストは守りたい挙動で命名し、過去バグの経緯は書かない
- **複数行コメントは意味の区切りで改行する**: 行幅で機械的に折り返さず、文・節（句読点）の区切りで改行する。1 行が多少横に伸びてもよい

## フォールバック禁止の具体例

| 禁止パターン | 例 | 問題 |
|---|---|---|
| 必須データのフォールバック | `user?.id ?? 'unknown'` | エラー状態で処理が続行される |
| デフォルト引数の悪用 | 全呼び出し元が省略する `function f(x = 'default')` | 値の出処が不明 |
| try-catch で空を返す | `catch { return ''; }` | エラーの握りつぶし |

許容: 外部入力バリデーション時のデフォルト値、設定ファイルのオプショナル値

## コメント禁止パターンの具体例

| 禁止パターン | 例 | 代わりに |
|---|---|---|
| 経緯・変更履歴 | 「以前は name のみ対応で全員配信になっていた」 | 現在の制約を書く:「admin の保存フィールドと一致させる。欠けると throw」 |
| 出自メモ | 「X から移植」「X と対」 | 同期が必要なら契約として書く:「X と対応を揃えること」。不要なら書かない |
| 修正の正当化 | 「これにより二重送信が直る」 | PR 本文へ |

許容: 現在形で書ける同期契約・制約・不変条件（「X と揃えること」「ここで throw しないと全員配信になる」）

## 報告・説明の書き方

- 作業の区切りでは「①何を変えたか(1〜3行) ②検証結果(実行したコマンド・確認手段) ③ユーザーが確認/判断すべきこと ④成果物リンク(PR 等)」を明示して終える。
- 「完了した・反映した・直った」と言う前に外部実体で検証する: PR は `gh pr diff`、push は `git log origin/<branch>`、デプロイは Actions 結果+実エンドポイント、網羅チェックは走査した件数・範囲を提示する。
- 説明・ドラフトは主語と対象を明示し、指示語だけで受けない。一文だけで読み手が理解を完結できるように書く。
- 「一旦」「とりあえず」のような留保表現で濁さない。複数案あるなら推奨を 1 つ明示する。
- 外部に貼るテキストは Markdown の表・`>`・`|` を使わずプレーンテキストで出す。
- 技術的断定（できない/こう動く）には公式ドキュメント等の一次ソースを添える。外部 API の仕様はリポジトリ内の既存値でなく、公式ドキュメントか実呼び出しで確認する。
- ユーザーが共有したリンク・エラー文・非推奨通知の内容は必ず取り込み、それが否定するものを再提案しない。

## 作業の進め方

- 調査・設計を求められたら複数案(目安 3 つ)+推奨をセットで提示し、実装前に擦り合わせる。プロジェクトが自走を指定している場合は、案を並べずに推奨を選び、根拠を 2-3 行添えて進む。
- PR・リリースのマージは、そのタスクでユーザーが明示的に許可した場合だけ行う。「PR 作成まで」「自分でマージする」の指定や、CI 成功だけではマージしない。既にそのマージが許可されていれば、指定条件を確認して進める。
- 設定・MCP サーバーの追加は既定でリポジトリスコープ。`~/.claude.json` 等 user スコープの変更は理由を添えて確認してから行う。
- 入力には音声文字起こし由来の誤変換が混じりうる。文脈から意図を汲み、意味が反転しうる箇所のみ確認する。
- コメント・ドキュメントに数値・コスト・設定値などの具体値を複製しない（変更に追従できず嘘になる）。

## 再利用できる知識の自動保存

説明・図解・調査で、汎用的な知識、長く使える知識、後から見返す可能性がある内容をまとめたら、ユーザーの「残して」を待たず show-me の保存手順で `~/visual-notes/` へ保存・登録する。既存の同じ題材は更新を優先し、その場だけの進捗や操作確認は保存しない。「保存しない」という指定は守る。リポジトリ内で発動した資料には、Git 設定で確認した発動元リポジトリ名のタグを付ける。タグ・別名は `~/visual-notes/catalog.json` の中央台帳で一元管理し、リポジトリ別の台帳を作らない。保存後は成果物リンクを短く報告する。

## 他の AI への相談経路

Claude Code から「Codex / Grok に相談して・聞いて・確認して」という依頼は、Claude 用の `consult-ai-cli` スキルでローカルの `codex` / `grok` CLI を直接使う。ブラウザ、Orca Computer Use、Codex Computer Use、GUI ターミナル操作で Web チャットへ質問しない。ユーザーが Web 版や既存のブラウザ会話を明示した場合のみ指定経路を使う。CLI が失敗しても UI へ暗黙に切り替えない。
