# Multi-Reviewer

リポジトリの default ブランチと現在のローカルの差分に対して、複数の AI ツール（codex, gemini cli, coderabbit）を用いて多角的なコードレビューを並列で実行し、その結果から必要性を判断して修正を適用し、最終的なレポートを作成するスキルです。

## フロー詳細

以下の手順に沿って実行してください。

### 1. デフォルトブランチの取得と差分確認

- リポジトリの default ブランチ（例: `main` や `master` など）を取得してください。
- default ブランチと現在のローカル環境の差分を取得してください。

### 2. 利用可能なツールの確認

- 以下の CLI ツールがシステムにインストールされ、実行可能であるかを確認してください。
  - `codex`
  - `gemini`
  - `coderabbit`
- インストールされているツールのみを、次のレビュー工程で使用します。
- 上記に加えて **Claude subagent（現行の最上位モデルを指定した code-review 系サブエージェント）** をレビュアーとして使えます。CLI ツールが 1 つも無い環境でも、Claude subagent 単独でレビューを成立させられます。

### 3. 並列レビューの実行

- 各ツールに対して、以下の4つの観点を重点的にレビューするよう指示を出してください。
  1. 一般的なベストプラクティスに沿ったものになっているか
  2. セキュリティ的に問題ないか
  3. パフォーマンスの懸念はないか
  4. リポジトリの設計に反したコードになってないか
- **必須要件:** 複数の観点を一度に問い合わせるのではなく、**各ツール × 各観点 ごとに独立したコマンドとして、すべて並列で実行**してください。これにより、AIがそれぞれの観点に深くフォーカスでき、より精度の高いレビューが可能になります。

**各ツールのコマンド仕様:**

各ツールはパイプ入力の対応状況が異なる。ツールごとに正しい呼び出し方を使うこと。

- **Codex CLI** (`codex exec` + コマンド置換):
  `codex review` は `--base` 指定時にプロンプトを受け付けないため、観点別レビューには使えない。
  代わりに `codex exec` を使う。**パイプではなくコマンド置換で差分をプロンプトに埋め込む。**
  パイプや `2>` リダイレクトと組み合わせると引数パースエラーになるため、必ず以下の形式を使うこと。
  ```
  # 1. 事前に差分をファイルに保存（1回だけ、全観点で共有）
  git diff <default-branch> > /tmp/multi-review-diff.patch

  # 2. コマンド置換でプロンプトに含め、stdout リダイレクトで結果を保存
  codex exec "$(cat /tmp/multi-review-diff.patch)

  上記の差分を【セキュリティの観点】からレビューしてください" > /tmp/codex-security.txt
  ```

- **Gemini CLI** (パイプ可、positional prompt):
  stdin でパイプ入力を受け付ける。`-y` で確認プロンプトをスキップする。
  ```
  git diff <default-branch> | gemini -y "以下の差分について、【パフォーマンスの観点】からレビューしてください"
  ```

- **CodeRabbit CLI** (ツールネイティブ):
  `coderabbit review` でリポジトリのレビューを実行する。観点指定オプションがあればそれを使う。

- **Claude subagent** (Agent ツール):
  現行の最上位モデルを指定してサブエージェントを起動し、差分と観点をプロンプトで渡してレビューさせる。
  観点ごとに独立したサブエージェントを並列で起動する。

各ツールごとに、上記のコマンドを **観点ごとに分けて並列で** 実行する。

### 4. レビュー結果の受け取りと判断

- 各ツールからのレビュー結果が出揃ったら、内容を統合・整理してください。
- それぞれの指摘事項に対して、「修正が必要かどうか（妥当か）」を判断してください。

### 5. 対応（修正）の実行

- ステップ4で「必要」と判断した指摘事項について、該当ファイルに変更を適用（修正）してください。

### 6. 最終レポートの報告

- 最後に、全体的にまとめたレポートをユーザーに報告して完了としてください。レポートには以下を含めてください。
  - 実行したツールとそれぞれの総評
  - 指摘された主要な問題点と、どの観点の指摘か
  - 実際にコードに適用した対応内容
  - 対応を見送った指摘があれば、その理由

## 収束レビューループモード

ユーザーが「問題なくなるまで修正とレビュー」「レビューループ」のように **収束まで** を求めたときは、上記フローを 1 ラウンドとして次のループで実行してください。

1. **ラウンド実行**: ステップ 1〜5（差分取得 → 並列レビュー → 判断 → 修正）を 1 ラウンドとして実行する。
2. **収束判定**: そのラウンドで「修正が必要」と判断した指摘が **ゼロ** なら収束。ステップ 6 の最終レポートに進む。
3. **再レビュー**: 修正を適用した場合は、修正後の差分に対して次のラウンドを実行する。指摘ゼロになるまで繰り返す。
4. **ラウンド上限**: 上限は **5 ラウンド**（ユーザー指定があればそちらを優先）。上限に到達したら、残っている指摘を「指摘内容 / 対応しない場合のリスク / 推奨対応」の形で列挙し、続行するかをユーザーに確認して停止する。上限到達を黙って収束扱いにしない。

**収束後のオプション:**

- 収束した時点でユーザーが PR 作成まで求めていた場合（またはここで希望を確認して求められた場合）は、`pr` / `create-pr` スキルに接続してブランチ作成・コミット・PR 作成まで行う。
- 求められていなければ最終レポートで終了する。
