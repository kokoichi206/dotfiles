# ADR フォーマット

ADR は `docs/adr/` 配下に置き、連番命名する: `0001-slug.md`, `0002-slug.md` ...

`docs/adr/` は **遅延作成** する。最初の ADR が必要になった時点で作る。

## テンプレート

```md
# {決定の短いタイトル}

{1〜3 文: 何が文脈で、何を決め、なぜそう決めたか}
```

これだけ。ADR は 1 段落で済むこともある。価値は「決定が行われた事実」と「その理由」の記録にある。セクションを埋めることに価値があるのではない。

## 任意セクション

以下は本当に価値が出る場合のみ含める。多くの ADR では不要:

- **Status** frontmatter (`proposed | accepted | deprecated | superseded by ADR-NNNN`) — 決定が見直されるときに有用
- **Considered Options** — 却下した代替案が記憶に値するときのみ
- **Consequences** — 自明でない下流の影響を明示する必要があるときのみ

## 番号付け

`docs/adr/` 内の最大番号を走査し、1 を加える。

## ADR を提案するタイミング

以下 3 つがすべて成立しなければ提案しない:

1. **元に戻しにくい** — 後で考えを変えるコストが意味のある大きさになる
2. **文脈なしには驚く** — 将来の読者がコードを見て「なぜこんな実装なのか」と疑問に思う
3. **本物のトレードオフの結果** — 実在する代替案があり、特定の理由で 1 つを選んだ

決定が容易に元に戻せるなら、ADR にしない。どうせ後で戻すだけ。驚かない決定なら、誰も理由を疑問に思わない。本物の代替案が無かったなら、「自明な選択をした」以上に記録すべきことが無い。

### 該当する典型例

- **アーキテクチャの形状。** 「monorepo を採用する」「書き込みモデルは event-sourced、読み込みモデルは Postgres に projection する」
- **コンテキスト間の統合パターン。** 「Ordering と Billing は同期 HTTP ではなくドメインイベントで通信する」
- **ロックインを伴う技術選択。** データベース、メッセージバス、認証プロバイダ、デプロイ先。すべてのライブラリではなく、入れ替えに四半期かかるものだけ。
- **境界とスコープの決定。** 「Customer データは Customer コンテキストが所有し、他のコンテキストは ID 経由でしか参照しない」明示的な NO は YES と同じくらい価値がある。
- **明らかな道からの意図的な逸脱。** 「ORM ではなく手書き SQL を使う、理由は X」妥当な読者が逆を仮定するであろうことすべて。これは次のエンジニアが「修正」しようとするのを止める。
- **コードに現れない制約。** 「コンプライアンス要件により AWS が使えない」「パートナー API 契約によりレスポンスは 200ms 以下」
- **却下された代替案 (却下理由が自明でない場合)。** GraphQL を検討して微妙な理由で REST にした場合は記録する。さもなければ半年後に誰かが再び GraphQL を提案する。
