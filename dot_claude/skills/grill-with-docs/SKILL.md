<what-to-do>

合意に至るまで、この計画のあらゆる側面についてユーザーを徹底的にインタビューする。設計ツリーの各分岐を順番に下り、決定間の依存関係を 1 つずつ解決していく。各質問について、あなたの推奨する回答も合わせて提示する。

質問は **一度に 1 つずつ** 行い、各質問へのフィードバックを待ってから次に進む。

コードベースを探索すれば答えられる質問は、ユーザーに尋ねる代わりにコードベースを探索する。

</what-to-do>

## ドメイン認識

コードベースを探索する際は、既存のドキュメントも併せて確認する。

### ファイル構造

ほとんどのリポジトリは単一コンテキスト構造を採る:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `CONTEXT-MAP.md` が存在する場合、そのリポジトリは複数コンテキストを持つ。マップは各コンテキストの所在を指す:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体の決定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← コンテキスト固有の決定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは **遅延作成** する。書くべき内容が出てから作る。`CONTEXT.md` が無ければ最初の用語が解決された時点で作る。`docs/adr/` が無ければ最初の ADR が必要になった時点で作る。

## セッション中の振る舞い

### 用語集との突き合わせ

ユーザーが `CONTEXT.md` の既存用語と矛盾する語を使ったら、その場で指摘する。「あなたの用語集では `cancellation` は X と定義されているが、いま Y の意味で使っていないか? どちらが正しい?」

### 曖昧な言葉を鋭くする

ユーザーが漠然とした、または多義的な語を使ったら、より正確な正準語を提案する。「いま `account` と言ったが、それは Customer のことか、それとも User のことか? それらは別物だ」

### 具体的なシナリオで議論する

ドメイン関係を議論しているときは、具体的なシナリオでストレステストする。境界ケースを探るシナリオを発明し、概念間の境界についてユーザーに正確さを強いる。

### コードと照合する

ユーザーが「これはこう動く」と述べたら、コードがそれと一致するか確認する。矛盾を見つけたら表面化する。「あなたのコードは Order 全体をキャンセルするが、いま部分キャンセルは可能だと言った。どちらが正しい?」

### CONTEXT.md をインライン更新する

用語が解決されたら、`CONTEXT.md` をその場で更新する。バッチで溜めず、発生のたびに記録する。フォーマットは [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) に従う。

`CONTEXT.md` は実装の詳細を **完全に排除** すること。`CONTEXT.md` を仕様書、スクラッチパッド、実装決定の置き場として扱わない。あれは用語集であり、それ以上の何物でもない。

### ADR は抑制して提案する

ADR の作成を提案するのは、以下の 3 つがすべて成り立つときに限る:

1. **元に戻しにくい** — 後で考えを変えるコストが意味のある大きさになる
2. **文脈なしには驚く** — 将来の読者が「なぜこの方法を選んだのか」と疑問に思う
3. **本物のトレードオフの結果** — 実際に複数の選択肢があり、特定の理由で 1 つを選んだ

3 つのうち 1 つでも欠ければ、ADR を作らない。フォーマットは [ADR-FORMAT.md](./ADR-FORMAT.md) に従う。
