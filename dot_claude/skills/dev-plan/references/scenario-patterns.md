# 受け入れシナリオ（scenarios.md）の書き方

**シナリオは「振る舞い」を記述する。実装詳細（セレクタ、ライブラリ名、API 名、関数名）は書かない。**

## 基本形式: Given / When / Then

```markdown
## S1: {1 文で書ける焦点絞ったシナリオ名}
- **Given**: 前提条件（状態、データ、画面）
- **When**: 操作（ユーザー行動、API 呼び出し）
- **Then**: 観測可能な結果
  - {期待値 1}
  - {期待値 2}
```

### S1, S2, ... の ID が必須

- Layer 1 で scenarios ↔ tests の対応チェックに使われる
- テスト名にも ID を含めること（例: `test('S1: ...', ...)`)

### One Sentence Without 'And'

シナリオ名は「And を使わず一文」で書けること。
書けないなら 2 つに分割する。

## 良い例 vs 悪い例

### 例 1: ログイン機能

✅ **良い（振る舞い）:**

```markdown
## S1: 正しい認証情報でログイン成功
- Given: DB に `user@test.com / password` のユーザーが存在する
- When: ログイン画面でメール・パスワードを入力してログインを実行
- Then:
  - ダッシュボード画面に遷移する
  - ウェルカムメッセージにユーザー名が表示される
  - セッションが確立されている（次回アクセスで再ログイン不要）
```

❌ **悪い（実装詳細）:**

```markdown
## S1: ログインボタンクリックで /dashboard へリダイレクト
- Given: POST /api/auth で 200 が返る状態
- When: [data-testid="login-btn"] をクリック
- Then:
  - window.location.pathname === '/dashboard'
  - Redux store の user が更新される
  - localStorage に 'token' が保存される
```

悪い例の問題:
- セレクタ (`data-testid`) を仕様レベルで指定している → 実装を縛る
- 内部状態 (Redux store, localStorage) を仕様に含めている → リファクタで壊れる
- API パスを指定している → バックエンド実装を特定のルートに縛る

良い例は **「ユーザーにとって何が起きるか」** のみを書いている。

### 例 2: データの状態変化

✅ **良い:**

```markdown
## S2: 商品追加でカート件数が増える
- Given: カートが空の状態で商品一覧画面を開いている
- When: いずれかの商品の追加操作を行う
- Then:
  - カート件数表示が 1 になる
  - 画面を再読み込みしても件数 1 が維持される
```

❌ **悪い:**

```markdown
## S2: addToCart() で state.cart.length が +1 される
- Given: useCart() が [] を返す
- When: onClick={handleAdd} が発火する
- Then: setCart() が呼ばれる
```

### 例 3: エラー処理

✅ **良い:**

```markdown
## S3: 不正なメール形式でエラー表示
- Given: 新規登録画面を開いている
- When: メール欄に "not-an-email" を入力して送信
- Then:
  - メール欄の直下にエラーメッセージが表示される
  - 新規登録は成立していない（次画面に進まない）
```

❌ **悪い:**

```markdown
## S3: zod の email validator が fail
- Given: form state が {email: "not-an-email"}
- When: schema.parse() を呼ぶ
- Then: ZodError が throw される
```

## 禁止ワードとその代替

| 禁止 | 代替 |
|---|---|
| セレクタ名（`data-testid`, `.class`, `#id`） | 「〜ボタン」「〜欄」「〜が表示される」 |
| ライブラリ名（React, Redux, Vue, ZodError 等） | 「画面」「状態」「エラー」 |
| 内部 API 名（useSomething, setSomething） | ユーザー操作の結果で書く |
| URL パターン（/api/xxx, /path/yyy） | 「〜画面に遷移」「〜情報が取得できる」 |
| 技術スタック名（JWT, cookie, localStorage） | 「次回アクセスで再ログイン不要」「セッションが維持される」 |

## 振る舞いタイプ別テンプレート

### ナビゲーション系

```markdown
## SN: {画面 A} から {画面 B} への遷移
- Given: {画面 A} を表示
- When: {ユーザー操作}
- Then: {画面 B} に遷移する、{画面 B} の主要要素が見える
```

### 状態変化系

```markdown
## SN: {操作} で {値 or 表示} が変化する
- Given: {初期状態}
- When: {操作}
- Then: {値 or 表示} が {期待値} に変化する
  - 変化は永続的（再読み込み後も維持される）
```

### 条件表示系

```markdown
## SN: {条件} のとき {要素} が表示される
- Given: {条件を満たす状態}
- When: {画面を開く}
- Then: {要素} が表示される、{他要素} は表示されない
```

### バリデーション系

```markdown
## SN: {不正入力} で {エラー表示}
- Given: {入力画面}
- When: {不正な値} を入力して送信
- Then:
  - {該当箇所} の近くにエラーメッセージが表示される
  - 送信は成立していない
```

### 外部連携系（API、DB 等）

```markdown
## SN: {外部サービス障害} 時の挙動
- Given: {外部サービス} が応答しない状態
- When: {ユーザー操作}
- Then:
  - ユーザー向けエラーメッセージが表示される
  - アプリはクラッシュしない
  - リトライ手段が提供される
```

## シナリオの網羅性（タスクタイプ別最低数）

| task_type | 最低シナリオ数 |
|---|---|
| ui-new | 正常系 2+ 異常系 2+ エッジ 1 = **計 5+** |
| ui-change | 新シナリオ 1+ 既存回帰 1 = **計 2+** |
| backend | 正常系 2+ 異常系 1 = **計 3+** |
| bugfix | 回帰テスト 1+ 周辺回帰 1 = **計 2+** |
| refactor | 振る舞い不変 1+ = **計 1+** |

## 不明点の列挙

scenarios.md の末尾に `## 要確認` セクションを設けて、LLM が気づいた曖昧さを列挙する:

```markdown
## 要確認
- Q1: 連続ログイン失敗時のロックアウト要件はありますか？
- Q2: セッション有効期限は何分ですか？
- Q3: 管理者ユーザーと一般ユーザーの遷移先は同じですか？
```

人間はこれを見て回答するか、現時点の仮定を承認する。
