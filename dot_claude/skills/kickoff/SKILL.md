# kickoff — 着手前の未知潰し

実装を始める前に、ユーザーの頭の中にだけある基準（無自覚の既知）と、まだ誰も決めていない事項（未知）を洗い出して固定する。
成果物を見せた後に基準が後出しされる往復を防ぐことが目的。

## 原則

- **コードベース・リポジトリ・渡された資料を探索すれば分かることは聞かない。** 自分で調べる。
- 質問は **一度に 1 つずつ**、自分の推奨案を添えて行う。
- **回答次第で設計が変わる質問を優先する**（データモデル・型インターフェース・UX フロー > 内部実装の詳細）。
- 質問は多くて 5 つ程度。網羅より「高くつく未知を先に潰す」を優先する。

## 手順

### 1. blindspot pass

指示文を読み、以下の観点で「書かれていないこと」を列挙する:

- **完了条件**: 何がどうなったら完了か。マージまでか、PR 作成までか
- **検証方法**: 誰が・どの環境で・何を見て確認するか。エージェント側で完結できる検証は完結させる前提で提案する
- **環境・対象**: dev/prod、aws profile、対象リポジトリ・ブランチ・デバイス
- **守るべき既存仕様・制約**: 既存挙動との整合、消してはいけないもの、ログ・命名などのポリシー
- **手元資料**: ユーザーが持っていそうな一次情報（先方の原文、エラー全文、メモ、スクショ、参照実装）。ありそうなら「あれば貼ってほしい」と明示的に要求する
- **スコープ外**: やらないことの境界

### 2. インタビュー

未決事項を影響の大きい順に 1 問ずつ質問する。
UI・見た目が絡む判断は、文章で質問するより HTML 複数案（ui-mockups の型）を先に出して反応で選ばせる方を優先する。

### 3. 着手メモの固定

合意した内容を以下の形式で提示し、OK をもらってから実装に入る:

```
## 着手メモ
- 目的:
- 完了条件:
- 検証方法（誰が・どの環境で・何を見て）:
- 環境・対象:
- 制約・守るべき既存仕様:
- 参照（現物コード・資料）:
- スコープ外:
```

タスクを別セッション・別エージェントに引き継ぐ場合は、このメモをファイルに書き出して渡す。

### 4. 実装中の逸脱記録

実装中にプランから逸れざるを得ない事象に当たったら、保守的な選択肢を選び、着手メモの下に **Deviations** 見出しで記録してそのまま進める。
完了報告には Deviations を必ず含める。

## 使い分け

- 分岐の多い設計判断そのものを詰めたい場合は grill-me（質問攻め）を使う。
- kickoff は「実装依頼を走らせる前の 5 分」を想定した軽量版。
