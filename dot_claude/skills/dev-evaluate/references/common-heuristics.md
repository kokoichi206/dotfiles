# 非 UI タスク向け Layer 3 チェックリスト

backend / refactor / bugfix の Layer 3 で使う構造化チェックリスト。
LLM に **pass/fail** を返させる。自由記述でスコアさせない。

## 全タスク共通: scenario ↔ assertion 対応

**必須チェック項目（全タスクタイプで評価）:**

scenarios.md の各シナリオ（S1, S2, ...）について、対応するテストの assertion が
Then 節の期待値を実際に検証しているか確認する。

- [ ] S1 のテストが S1 の Then を検証する assertion を持つ（単なる true/truthy チェックではない）
- [ ] S2 のテストが S2 の Then を検証する assertion を持つ
- [ ] ...（全シナリオについて繰り返し）
- [ ] テスト名は ID 対応しているが、中身が空・コメントのみ・無関係な assertion のテストがない
- [ ] Mock / Stub がシナリオの検証を骨抜きにしていない（例: 全てを mock して「通した」状態になっていない）

**判定例:**

scenarios.md:
```
## S1: 正しい認証情報でログイン成功
- Then: ダッシュボードに遷移、ウェルカムメッセージが表示
```

acceptance-tests/auth.spec.ts:
```typescript
test('S1: 正しい認証情報でログイン成功', async ({ page }) => {
  await page.goto('/login');
  // ...操作...
  await expect(page).toHaveURL('/dashboard');       // ← URL 遷移を検証 ✓
  await expect(page.getByText(/ようこそ/)).toBeVisible();  // ← welcome 表示を検証 ✓
});
```
→ **pass**（Then の 2 項目をそれぞれ assertion で検証している）

```typescript
test('S1: 正しい認証情報でログイン成功', async ({ page }) => {
  await page.goto('/login');
  // ...操作...
  expect(true).toBe(true);  // ← 何も検証していない
});
```
→ **fail**（空の assertion、Then を検証していない）

## backend タスク

### エラーハンドリング

- [ ] 暗黙的 fallback（`?? 'unknown'`, `catch { return '' }` 等）がないか
- [ ] エラーは上位層で集中処理されているか（try-catch が散らばっていない）
- [ ] 外部 API 呼び出しに timeout 設定があるか
- [ ] バリデーションがシステム境界（入力層）で行われているか

### コード品質

- [ ] 関数が単一責任か（1 関数 = 1 目的）
- [ ] 命名が意図を明確に表しているか
- [ ] マジックナンバーが定数化されているか
- [ ] 深いネスト（3 段以上）が早期リターンで解消されているか

### 設計

- [ ] 不要な抽象化（単一実装のインターフェース等）がないか
- [ ] 未使用コード（未使用 import, 到達不能コード）がないか
- [ ] CLAUDE.md の「念のため」コード禁止に準拠しているか
- [ ] コメントが Why のみで What/How を説明していないか

### セキュリティ

- [ ] SQL インジェクション対策（パラメータ化クエリ）があるか
- [ ] ユーザー入力が信頼されずにサニタイズされているか
- [ ] 認証・認可のチェックが漏れていないか
- [ ] 機密情報（API キー、パスワード）がコードに含まれていないか

---

## refactor タスク

- [ ] 振る舞い変更がないか（既存テストが全件パス）
- [ ] DRY の解消が妥当か（同じビジネス概念のみ統合、表面的な類似は統合しない）
- [ ] 命名が改善されているか
- [ ] 複雑度（ネスト、分岐）が削減されているか
- [ ] 「次のタスクで」先送りされていない Boy Scout Rule 違反の解消
- [ ] 抽象化の妥当性（YAGNI 違反がない）

---

## bugfix タスク

### 原因分析

- [ ] 根本原因が特定されているか（PR description or コミットメッセージに記載）
- [ ] 表面的な症状ではなく原因に対する修正か
- [ ] 暗黙的 fallback で「とりあえず動く」にしていないか

### テスト

- [ ] 回帰テストが追加されているか
- [ ] そのテストが修正前は FAIL、修正後は PASS を確認できるか
- [ ] 類似のバグが防げるよう境界値・異常系もカバーしているか

### 影響範囲

- [ ] 修正が意図した箇所のみに限定されているか
- [ ] 他の機能への副作用が確認されているか
- [ ] 再発防止策（型安全性、バリデーション強化等）が検討されているか
