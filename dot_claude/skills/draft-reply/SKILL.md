# 返信・報告文ドラフト

チャット・メールなど外部に送る文面を下書きする。宛先と媒体のトーンに合わせて整形する。

## 重要: 応答規約とドラフト内容は別

- グローバル設定の「絵文字・派手な表現を使わない」は **Claude からユーザーへの応答**の規約であり、
  **ここでドラフトする文面には適用しない。** 宛先・チャネルのトーンに合わせる（カジュアルな Slack では
  絵文字や「！」を使ってよい。硬い連絡では使わない）。
- この SKILL 本文（Claude の説明）自体は規約どおり絵文字を使わない。区別する。

## 手順

1. **要点を抽出する**
   会話文脈から、相手に伝える/尋ねる要点を洗い出す。

2. **宛先と媒体を推定・確認する**
   誰宛て（顧客 / PM / 社内）で、どの媒体（Chatwork / Slack / メール）かを推定する。不明なら確認する。

3. **過去の実送信文面を探す**
   同じ相手・同じ媒体へ過去に送った文面がリポジトリにあれば Grep で探し、**書式ごと**合わせる。
   見出しの記法（`【】`）、出典の書き方（`ref: URL`）、条文引用の出し方は、言い回しより先に真似る。
   相手のメールに引用されている「自分が前に送った文章」も一次サンプルとして使える。

4. **媒体に合わせて整形する**
   - **Chatwork**: Markdown 非対応。箇条書きは `・` を使う。素の敬語。
   - **Slack**: 見出しは `【】`、その下に箇条書き。カジュアルな相手なら絵文字・「！」可。
   - **メール**: プレーンテキスト。Markdown 記法（表・`>`・`|`・`#`）を使わない。宛名と署名を付ける。
   - ユーザーが書式を指定した場合はそちらが優先。上のルールと衝突しても指定に従う。

5. **humanize-ja を Read してから文面を整える（必須）**
   - このステップに入る前に、必ず humanize-ja の SKILL.md を **Read ツールで開く**。
     パス: `~/.claude/skills/humanize-ja/SKILL.md`
   - 記憶・要約・「だいたい知っている」で代替しない。ファイルを読んだうえで、
     humanize-ja の手順（パターン列挙 → 下書き → 自己監査 2 問 → 最終稿）を踏む。
   - 分担: 媒体整形（Chatwork / Slack / メール）はこの skill。文体・リズム・AI 臭除去は humanize-ja。
   - 主語と対象を明示し、指示語だけで受けない。一文で意味が通るようにする。

6. **質問返しは番号を振る**
   相手に複数確認するときは番号付きにして、答えやすくする。

7. **複数案は 3 つ + 推奨**
   トーン違い等で複数案を出すときは 3 案にし、推奨を 1 つ明示する。

8. **ファイルに書き出す**
   長い文面・確定前の下書きは、コピーしやすいようファイルへ書き出す。
   送信本文と社内用の根拠は 1 ファイルにまとめ、区切り線で分ける。同じ内容の `.txt` と `.md` を並べない。

## 構成の原則

- **結論を 1 行目に置き、理由は括弧か参照リンクに落とす。** 相手が知りたいのは可否で、理由は納得材料。
  相手の質問を順番どおり章立てにすると、説明が主役になって読み手の負荷が上がる。
- **相手が次に何を判断・実行するかから逆算する。** 網羅は社内用の根拠セクションへ逃がす。
- **否定的な回答では、「できない」の分量が全体を占めていないか最後に確認する。**
  同じ理由に帰着する否定は 1 つにまとめる。締めは相手に求めるアクションで終える。
- **相手が既に知っている案・相手から出た案を再提案しない。** 「さっき聞いた」と読まれる。
- **条文・URL・引用は独立したブロックに置く。** 顧客向けの回答は社内で転送されるため、切り貼りできる形にする。
- **「簡潔に」「AI っぽい」と指摘されたら、語数を削るのではなく構造を組み直す。**
  段落の形が同じまま短くなるだけでは重心は動かない。
- **相手の質問を勝手に狭めない。** 「X の問題ではなく Y です」と書く前に、相手が本当に X を論点にしたか確認する。
  していなければ対比を消し、事実だけ書く。
