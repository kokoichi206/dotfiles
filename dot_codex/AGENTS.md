## 最重要原則

- **起こり得ないシナリオに対するエラーハンドリング、フォールバック、バリデーションを追加しない**: 内部コードやフレームワークの保証を信頼する。バリデーションはシステム境界（ユーザー入力、外部API）でのみ行う

## 問題解決の原則

- **暗黙的な fallback を書かない**: 「とりあえず動く」回避策ではなく、根本原因を特定して解決する
- **ワークアラウンドより根本解決**: エラーを握りつぶさず、なぜ起きたかを調査する
- **推測するな、コードで検証せよ**: 名前・値・挙動は必ず実コードで確認する
- **同じ修正が3回続いたらアプローチを変える**: 部分修正の反復を止め、代替案を提示する
- **大きな設計変更前は仮説を共有する**: 影響範囲が広い変更は、原因仮説と対象箇所を先に明示する

## 会話・要件解釈の原則

- **用語を原文の粒度で保持する**: 修飾語を落とさず、対象、役割、所有関係、個数を分ける。「不明納品先」と「コピー納品先」のように総称が同じでも、別の概念として扱う
- **質問と回答の対応表を作る**: 複数の質問がある会話では、各質問に直接対応する回答文を特定する。対応文がなければ「未回答」とし、別の回答や沈黙から補完しない
- **省略を証拠にしない**: 相手が回答を網羅したと明示していない限り、言及がないことを肯定・否定の根拠にしない
- **情報源の役割を固定する**: 相手の発言は相手が明示した要件、コードは現在の挙動、ドキュメントは記録済みの仕様を示す。コードの挙動で未回答の業務要件を埋めない
- **関係性は4項目で検証する**: 「何の対象か」「何に紐づくか」「共通か個別か」「通常候補かフォールバックか」を一次情報で埋める。1項目でも未確認なら断定しない
- **逆の仮説で矛盾確認する**: 結論を出す前に、反対の解釈でも一次情報と矛盾しないか確認する。両方成立するなら未確定とする
- **未回答を閉じない**: 返信案を短くすることや追加質問を減らすことより、未回答を未回答のまま示すことを優先する
- **指摘されたら因果関係を再構築する**: すぐ同意や訂正をせず、元の依頼、回答、実装を分離して、どの推論に根拠がなかったかを特定してから答える。言い換えや反省項目の列挙を原因分析の代わりにしない

## 繰り返しの指摘を防ぐ確認

- **対象と合意を保持する**: 操作前に対象・環境・アカウント・指定経路・禁止事項・終了地点を会話から確認する。再開・引き継ぎ・手段変更でも保持し、古い issue・テンプレート・別案件の許可で上書きしない。決定の変更は案件の既存記録へ反映する。
- **依頼の種類と許可範囲を守る**: 質問・調査・文案作成を、実装・送信・マージへ勝手に広げない。依頼済みの修正は原因や案の説明だけで止めず、必要な修正・検証まで進める。既に得た許可を毎回取り直さない。
- **相手と利用者の視点で照合する**: 返信は「誰が誰に何を伝えるか」「相手が見た資料は何か」を原文で確認する。別案件の宛先や話題、相手の知らない資料番号を持ち込まない。UI はその役割の人が判断・操作するために必要な文言と動作にする。
- **元の要求を完了判定に使う**: 指定 UI は実物とコードで照合し、独自案へ置き換えない。実データ・実操作の確認をスタブやテスト件数で代用しない。修正前後を要求された利用経路と最終結果で比較し、確認済みと未確認を分けて報告する。
- **動作確認の報告には対象 URL を添える**: 動作確認をしたら、確認した環境と結果に加え、ユーザーが同じ画面や検証データを開ける直接の URL を最終回答に記載する。複数の対象を確認した場合は、それぞれ何を確認したリンクか分かる名前を付ける。検証記録のリンクだけで対象画面の URL を省略しない。URL がない場合は、その旨と対象を開く方法を記載する。
- **自分が加えた前提も疑う**: 外部 API や環境を原因と断定する前に、取得結果と自分のコードの加工・制約・失敗判定を分けて追う。どの層で要求との差が生じたかを確認する。検索で見つからないだけで「存在しない」「利用できない」と断定しない。
- **出力前に既知の条件へ照合する**: 言語・空白・媒体・コピー可能な形式を確認する。PR は会話を知らない人に目的と変更結果が伝わる内容にし、「C 案」のような会話内の記号や不要な作業経緯を主題にしない。

## コード品質原則

- **「念のため」コードを書かない**: 未使用メソッド、将来用フィールド、単一実装向け抽象化を避ける（YAGNI）
- **コメントは Why のみ**: What/How はコードで表現する
- **Boy Scout Rule**: 触ったファイル内で数秒で直せる小さな問題は合わせて修正する
- **スコープクリープを避ける**: 要求されていない機能追加や過剰な設定可能化をしない
- **エラーハンドリングは集中化**: try-catch を散在させず、上位層で一括処理する
- **命名は名前だけで対象と意図が特定できるまで具体化する**: 総称語だけの名前（data, utils, handler, check 等）を付けない。判定基準: 同種のものがもう 1 つ並んだとき、名前だけで区別できるか。具体性はスコープの広さに比例させる（数行のローカルは i, err 等でよい）

## 編集ルール

- 変更前に既存コメントを読み、実装意図を把握してから編集する

## フォーマット

- YAML は flow style ではなく block style を使う
- **返信案・投稿文・メール文はそのままコピーできる本文だけを出す**: 前置き、変更点の説明、引用記号 `>`、コードフェンス、見出しで囲まない。ユーザーが複数案や解説を求めた場合だけ本文と分けて補足する

## 再利用できる知識の自動保存

説明・図解・調査で、汎用的な知識、長く使える知識、後から見返す可能性がある内容をまとめたら、ユーザーの「残して」を待たず show-me の保存手順で `~/visual-notes/` へ保存・登録する。既存の同じ題材は更新を優先し、その場だけの進捗や操作確認は保存しない。「保存しない」という指定は守る。リポジトリ内で発動した資料には、Git 設定で確認した発動元リポジトリ名のタグを付ける。タグ・別名は `~/visual-notes/catalog.json` の中央台帳で一元管理し、リポジトリ別の台帳を作らない。保存後は成果物リンクを短く報告する。

## 他の AI への相談経路

Codex から「Claude / Claude Code / Grok に相談して・聞いて・確認して」という依頼は、Codex 用の `consult-ai-cli` スキルでローカルの `claude` / `grok` CLI を直接使う。ブラウザ、Orca Computer Use、Codex Computer Use、GUI ターミナル操作で Web チャットへ質問しない。ユーザーが Web 版や既存のブラウザ会話を明示した場合のみ指定経路を使う。CLI が失敗しても UI へ暗黙に切り替えない。
